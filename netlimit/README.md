# NetLimit -- Internet Usage Control

A solution for limiting unnecessary internet use across a ~400-user
organization: category-based content filtering (social media, streaming,
gaming, shopping, adult, ...) combined with per-user/department daily
time and data quotas, a policy management dashboard, usage reporting, and
alerting.

This is a standalone project inside the repo (`netlimit/`) -- it does not
depend on or modify the existing OSINT app.

## How it fits together

Enforcement happens at the network edge (a caching proxy every user's
traffic goes through); this app is the brain that decides policy and tracks
usage.

```
                 +-------------------+
   All outbound   |   Squid proxy     |  400 client devices, transparently
   HTTP(S) ------>|  (network edge)   |<-- or explicitly proxied
                 +---------+---------+
                           |
              1. static ACLs (fast path):
                 category domain lists,
                 always-on department/user blocks
                           |
                           v
              2. external_acl_type -> squid_helper.py
                 (authoritative: checks live policy +
                  today's time/data quota via the DB)
                           |
                           v
                 +-------------------+
                 |  netlimit DB      |  Users, Departments, Categories,
                 |  (SQLite/Postgres)|  PolicyRules, UsageRecords, Alerts
                 +---------+---------+
                           ^
                           |
                 +-------------------+
                 |  NetLimit dashboard| <- admins manage policy, view
                 |  (this Flask app)  |    reports, get alerts
                 +-------------------+
```

* **Static ACLs** (generated by `squid_config.py`) give instant, cheap
  blocking for always-on rules (e.g. "Sales department never gets gaming
  sites"). Good enough on their own for pure content filtering.
* **`squid_helper.py`** is an `external_acl_type` helper that calls the same
  policy engine the dashboard uses, so it can enforce things static ACLs
  can't express: "block once today's 90-minute quota is used up" is a
  moving target that changes throughout the day.
* Squid's own **access log** is also parsed by `log_parser.py` for
  backfill/reporting and as a cross-check against what the helper recorded.

Why a proxy instead of pure DNS filtering: DNS blocking can stop a
domain but can't measure *how much* time/data was spent on the sites you
do allow, which is required for the quota half of this project. A
transparent HTTP(S) proxy (Squid, with SSL-bump for HTTPS domain visibility)
gives both category blocking and usage metering from one signal source.

## Data model

* **Department** -- default daily time (minutes) and data (MB) quota.
* **Category** + **CategoryDomain** -- e.g. `social_media` ->
  `facebook.com`, `instagram.com`, ... Subdomains match automatically.
* **User** -- belongs to a department, has an IP (how Squid identifies
  them), optional per-user quota override, `is_exempt` for IT admins/execs
  who should bypass all limits.
* **PolicyRule** -- `allow` / `block` / `time_restricted` for a
  (category, scope) pair, where scope is a department or a single user.
  **User-level rules always override department-level rules.**
* **UsageRecord** -- per user/category/day: minutes used, data used,
  blocked attempts. This is what quotas are measured against and what
  the reports/dashboard are built from.
* **Alert** -- auto-created once per day when a user crosses 80% (warning)
  or 100% (exceeded) of either quota dimension.

## Running the dashboard

```bash
cd netlimit
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python -m netlimit.seed              # creates 9 departments, default
                                      # policies, and 400 demo users
python -m netlimit.app               # dashboard on http://localhost:5050
```

## Hosting a demo for the client to test

The dashboard needs a live server process and a database, which rules out
Netlify (static hosting + stateless functions -- no fit for an app with
forms that write data). It deploys cleanly as a normal web service instead.

**Render (one click):**

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/gathuk/Shebe)

This uses `render.yaml` at the repo root -- free plan, no config needed
beyond clicking through with a Render account. First boot auto-seeds the
9 departments / 400 demo users (`netlimit/wsgi.py`).

**Railway:** connect the GitHub repo, it will pick up the root `Procfile`
(`web: gunicorn -w 2 -b 0.0.0.0:$PORT netlimit.wsgi:app`) automatically.
Set `NETLIMIT_DB_URL` if you want something other than the default SQLite
file.

**Free-tier caveat:** both platforms' free instances have an *ephemeral*
disk -- it resets on redeploys and after the instance spins down from
inactivity. `wsgi.py` reseeds demo data automatically whenever it boots to
an empty database, so the client always lands on a working demo, but any
policy/user edits made during a session won't survive an idle spin-down.
For a persistent instance the client can keep editing across days, either
upgrade to a paid plan with a persistent disk, or point `NETLIMIT_DB_URL`
at a hosted Postgres (e.g. Neon, Supabase) -- the app is already
database-agnostic via SQLAlchemy.

Set `NETLIMIT_DB_URL` to point at a real database in production, e.g.
`postgresql://user:pass@host/netlimit` (any SQLAlchemy URL works; swap
`sqlalchemy` for the appropriate DB driver in `requirements.txt`).

Run the test suite:

```bash
pip install pytest
pytest netlimit/tests -q
```

## Deploying enforcement (Squid)

1. Install Squid (and optionally `squid-openssl` for HTTPS SSL-bump so
   category ACLs can match HTTPS domains, not just plaintext HTTP).
2. From the dashboard, open **Squid Config** and download the generated
   `netlimit.conf`. Include it from the main config:
   ```
   include /etc/squid/netlimit.conf
   ```
3. Deploy `squid_helper.py` to the proxy host (e.g.
   `/opt/netlimit/squid_helper.py`), pointed at the same database via
   `NETLIMIT_DB_URL`, and make it executable. The generated config already
   wires it up via `external_acl_type`.
4. Point client devices at the proxy (WPAD/PAC file, or a transparent
   redirect via the firewall) and roll it out.
5. Re-download/re-deploy `netlimit.conf` whenever policy rules change
   (department/user block rules, new domains). Quota enforcement itself
   updates live -- no redeploy needed, since `squid_helper.py` reads current
   state from the database on every request.
6. Optionally, run `log_parser.ingest_log_file()` against Squid's
   `access.log` on a schedule (cron/systemd timer) as a reporting
   cross-check independent of the helper.

## Limitations / next steps for a production rollout

* **HTTPS visibility** requires SSL-bump (MITM at the proxy with a
  trusted internal CA pushed to client devices) to see hostnames for
  category matching; without it, only SNI-based domain matching is
  available (still works for category blocking, but request-level detail
  is more limited).
* **Category domain lists** here are small starter sets
  (`categories.py`). Production deployments should point at a maintained
  URL-categorization feed instead of hand-maintained lists, especially for
  the `adult` category.
* **"Active minutes"** from log parsing are inferred from distinct
  one-minute request buckets, not true dwell time -- a reasonable proxy
  for proxy-log-only environments, but a browser extension or endpoint
  agent would give more accurate active-time measurement if the client
  wants that level of precision.
* **Unregistered devices** (unknown source IP) default to being allowed
  through (`NETLIMIT_UNKNOWN_IP_POLICY=allow`) so guest Wi-Fi isn't
  silently cut off; set it to `deny` if the org wants a strict
  registered-devices-only policy instead.
